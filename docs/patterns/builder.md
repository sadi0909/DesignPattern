# Builder — Phase 4

## Problem

A greenhouse location is more than one field: its configuration contains a named location and one or more zones, each with a name, moisture-threshold range, and optional schedule. Saving a half-filled form or a loosely shaped dictionary risks storing a location with no zones or invalid moisture thresholds. Repeating those rules only in a browser or an HTTP handler also lets another caller bypass them.

## Solution

`LocationConfigBuilder` accumulates the location name and zone definitions through stepwise methods. Its `build()` method is the domain gate: it requires a non-empty location name, at least one zone, non-empty unique zone names, thresholds in the inclusive 0.0–1.0 range, and a low threshold strictly below the high threshold. Only a successful build returns the immutable `LocationConfig` aggregate. Invalid input raises the domain `ConfigurationError` before repository persistence begins.

The application service translates the request DTO into builder calls, calls `build()`, then asks `LocationRepository` to persist the location and all zones in one transaction. The API maps domain validation errors to HTTP 400 and the saved domain configuration to response DTOs. The dashboard wizard offers inline feedback for common input mistakes, but the domain builder remains authoritative.

## Builder vs Factory Method vs Abstract Factory

- **Factory Method** answers “which one product?” Phase 2 creators produce one configured sensor variant.
- **Abstract Factory** answers “which matching product kit?” Phase 3 creates a coherent simulation or edge kit of sensors and actuators.
- **Builder** answers “how do we assemble this valid whole in steps?” Phase 4 assembles one location-with-zones aggregate and validates it before it can be saved.

A fluent API (`with_location_name(...).add_zone(...).build()`) is a convenient method-chaining style; fluent methods alone do not make a class a Builder. The pattern's key contribution here is controlled accumulation plus final validation and a complete product.

## Persistence and naming

The persistence model uses `locations` and `zones`. Each zone has a required `location_id` foreign key to `locations.id`, with an index for retrieving a location's zones and cascading deletion. Saving a configuration adds the parent and children in one database transaction, so a failed zone insert cannot leave behind a location with no complete configuration. The course scope name is **`location_id`**; this phase does not introduce `greenhouse_id`.

## Extension exercise

Add a zone setting such as a light target or a descriptive note. Decide whether it belongs in the domain model, validate it in `LocationConfigBuilder.build()`, persist it in an autogenerated migration, and expose it through DTOs and the wizard. Keep invalid configurations from reaching the repository, and retain `location_id` as the parent scope key.
